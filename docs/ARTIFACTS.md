# Investigation archives and S3 adapter

The archive exports a terminal investigation, report, saved evidence and pinned configuration as bounded canonical JSON. Storage delivery runs separately from diagnosis. This is an operator-requested export, not automatic archiving of original documents or raw telemetry streams.

Start `scripts/start-stack.ps1 -LiveDemo -Knowledge -Agent -Artifacts` for the working local backend. It adds an uploader and two persistent Docker volumes: spool and local objects. It needs no AWS account. This filesystem backend shares the storage interface; it is not an S3 emulator or proof of AWS deployment.

Choose Archive investigation on a terminal case. The API flushes a temporary spool file and atomically renames it before inserting pending_upload metadata. Identity includes investigation, backend and SHA-256; identical requests reuse one row/key. JSON is capped at 5 MB and evidence arrays sort by immutable ID. Orphan spool files can remain after database insertion failure; automatic cleanup is deferred.

The uploader claims with PostgreSQL SKIP LOCKED, a token and sixty-second lease. It first verifies an existing stable object, reconciling an upload that succeeded before its database update. Otherwise it verifies the spool, writes the object, verifies stored checksum/size, then marks available with a lease-fenced update. Stale owners cannot finalize. A missing spool may be rebuilt from terminal database records only if the original checksum still matches. Corrupt bytes are never relabelled as a successful archive.

Failures stay pending with bounded delay, then failed after five claims, including repeated crashes. Explicit Retry archive resets delivery attempts; it does not retry diagnosis. Persisted errors are generic. Core investigation data remains in PostgreSQL. A download requires available metadata and verified bytes in the configured backend; missing/corrupt storage produces an explicit error. Available means verified at delivery, not immune to later operator deletion. External deletion/retention reconciliation is not automated.

The S3 adapter implements single PutObject with explicit SHA-256/AES256 encryption, HeadObject with checksum mode enabled, and five-minute SigV4 signed downloads. SDK retries are disabled; application delivery attempts own retries. Existing mismatched objects are rejected. It never creates buckets or modifies permissions. The pinned boto3/botocore SDK's offline Stubber checks passed in Python 3.12 Docker with networking disabled. Contract checks do not establish actual AWS connectivity.

No AWS resources, credentials or objects were configured by this increment. Before connection, prepare a private bucket/region and scoped server-side credentials; do not paste keys into chat. Enable Block Public Access, bucket-owner-enforced ownership, encryption and the intended retention policy. Restrict object access to exports/v1. Normal delivery needs scoped GetObject/PutObject, not ListBuckets or account administration. Follow the actual [PutObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_PutObject.html) and [HeadObject](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) permissions/checksum contracts.

Optional factory settings: ARTIFACT_BACKEND=s3, ARTIFACT_SPOOL_DIR, ARTIFACT_S3_BUCKET, AWS_REGION and ARTIFACT_S3_PRIVATE_CONFIRMED=1. Install requirements-artifacts.lock for host use. The optional Docker s3 target/compose.s3.yaml is defined for API/uploader; apply it after compose.artifacts.yaml only when the user completes private-bucket configuration. Its online dependency build/cloud runtime is not established by the separate offline SDK verification image. The confirmation flag is an operator assertion, not an automatic bucket audit. Only API/uploader receive AWS credentials; the investigator worker does not. No real S3 calls should occur before that setup. Old local exports remain listed when switching backends, but their download link is disabled while that backend is inactive.

Verified locally: outage/retry exhaustion, explicit retry, corrupt spool rejection, missing-spool reconstruction, object-first reconciliation, stale-owner rejection, checksum-gated downloads and PostgreSQL claim contention. The connected synthetic workspace completed and archived with zero model calls, including while Redis was stopped. Original-document archiving, spool cleanup, lifecycle reconciliation, multipart uploads, KMS and cross-region replication remain outside this artifact slice.

The S3 Compose override was also resolved successfully using a dummy bucket/region, without starting it. Only API/uploader select the S3 backend; worker receives no AWS credential variables and API receives no model key. This configuration check is separate from online image-build and actual cloud qualification.
